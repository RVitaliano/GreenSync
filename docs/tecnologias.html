1. Aplicativo Mobile

Característica Informação
Linguagem de programação Dart, linguagem do Flutter, usada para toda a interface e a lógica do aplicativo.
Framework / SDK Flutter (multiplataforma Android/iOS), com integração ao Firebase via FlutterFire e compilação Android voltada ao SDK 37+.
IDE / Ambiente Visual Studio Code; testes em aparelho físico Android com build de desenvolvimento e variáveis de ambiente via --dart-define.
Bibliotecas / Plugins firebase_core, cloud_firestore (leitura em tempo real e histórico), fl_chart (gráficos históricos), flutter_blue_plus (BLE) e permission_handler (permissões de Bluetooth/localização).
Integração com o projeto Lê a coleção devices no Firestore por listeners em tempo real (leitura atual, histórico e status online/offline), envia pedidos de rega e agendamentos ao backend por HTTP e envia credenciais Wi-Fi ao vaso via Bluetooth (BLE).

2. Sistema Embarcado / Firmware

O vaso utiliza dois microcontroladores com responsabilidades separadas.

Característica Informação
Placas e microcontroladores ESP32-WROOM-32 (sensores, bomba, MQTT, BLE e OTA) e Seeed Studio XIAO ESP32-S3 (voz: microfone, alto-falante e display OLED).
Linguagem de programação C++ (Arduino, com padrão -std=gnu++17).
IDE e Framework / SDK VS Code com PlatformIO (Core 6.2.0, Home 3.4.4) e framework Arduino-ESP32 (plataforma espressif32).
Sistema Operacional / RTOS FreeRTOS, nativo do Arduino-ESP32 sobre o ESP-IDF.
Bibliotecas e recursos principais WROOM: WiFiClientSecure (TLS), PubSubClient (MQTT), ArduinoJson 7, DHT sensor library / Adafruit Unified Sensor (DHT22), leitura analógica do YL-69 (ADC1), relé de 2 canais para a bomba, NimBLE-Arduino 2 (BLE), OTA com SHA-256, partições min_spiffs.csv (dois slots) e rollback automático. O pH é simulado (ADR-024).

S3: I2S (microfone INMP441 e amplificador MAX98357), U8g2 (display OLED SSD1306), ativação por voz local (ESP-SR / "Hi ESP") e cliente HTTP para o backend.

3. Plataforma IoT / Backend / Nuvem

Característica Informação
Local de hospedagem Provedor cloud Render (serviço web, instância única, sempre ativo, com health check em /health).
Linguagem e framework Python 3.12 (imagem python:3.12-slim) com FastAPI e uvicorn; concorrência com async/await em processo único e cliente MQTT assíncrono (aiomqtt).
Serviços e produtos EMQX Serverless (broker MQTT), Firebase Firestore (região southamerica-east1) com Firebase Admin SDK, Redis (Render Key Value — limite de perguntas e contexto curto da conversa), Google Gemini (google-genai — entendimento de texto/áudio e TTS) e GitHub (código, releases do firmware e GitHub Actions).
Implantação e orquestração Docker: mesma imagem roda no Render (deploy automático via branch main) e localmente via Docker Compose (backend, Mosquitto e Redis). Sem Kubernetes.
Persistência e administração Firestore (devices/{id}, historico, agendamentos e firmware/{alvo}). API protegida com X-API-Key (usuário) e X-Admin-Key (administração/OTA). Credenciais em variáveis de ambiente e Secret File fora do Git. Suíte com 973 testes automatizados em pytest.

4. Comunicação e Integração

Característica Informação
Protocolos utilizados MQTT (vaso ↔ backend: leituras, status, comandos e progresso de OTA), HTTP/HTTPS REST (app e S3 ↔ backend; áudio do assistente), BLE (configuração de Wi-Fi do vaso) e Firestore SDK em tempo real (backend ↔ app).
Broker / Gateway / Servidor EMQX Serverless (broker gerenciado, porta 8883); Mosquitto apenas no ambiente local.
Formato dos dados JSON nas mensagens MQTT, documentos Firestore e cabeçalhos auxiliares; WAV (16 kHz, 16 bits, mono) para áudio de entrada e WAV (24 kHz) para resposta falada.
Segurança de comunicação MQTT sobre TLS com usuário e senha (um usuário por papel); endpoints HTTP com X-API-Key/X-Admin-Key em comparação de tempo constante e limite de 10 perguntas por 60 s no Redis; OTA exclusivamente via HTTPS de github.com com verificação SHA-256. Pendente: validação do certificado CA no firmware e ACL por tópico no EMQX.
Fluxo entre camadas Vaso (WROOM) → MQTT/TLS → EMQX → Backend (FastAPI) → Firestore → App Flutter. Comandos de rega seguem o caminho inverso (App → Backend → MQTT → Vaso). Voz: S3 → HTTPS POST /audio → Backend → Gemini → áudio de resposta ao S3.

5. Case / Invólucro do Produto

Característica Informação
Software de modelagem 3D OpenSCAD (modelagem paramétrica por código), com fatiamento no Anycubic Slicer Next.
Formato dos arquivos SCAD (fonte paramétrica), STL (malha exportada) e 3MF / G-code (fatiamento).
Processo de fabricação Impressão 3D FDM realizada na impressora Anycubic Kobra 3 V2.
Material e parâmetros Filamento PLA ou PETG; altura de camada de 0,2 mm, preenchimento de 30% com padrão Giroide e suportes tipo árvore (Tree) para integridade das travas.
Integração mecânica Estrutura de 120 mm com divisórias internas e presilha reforçada (8 mm de espessura × 40 mm de largura). Acomoda os dois ESP32, protoboards, módulo relé de 2 canais, bomba d'água e alimentação de 5 V; possui encaixes dedicados para o sensor DHT22 no topo da tampa, microfone INMP441 e display OLED SSD1306, além da passagem da sonda YL-69 para o solo.
